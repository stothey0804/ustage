# 요금제·유료 기능 범위 계획 (미착수 — 착수 전 이 문서부터 읽는다)

작성 2026-08-31 · 상태 **미착수** · 현재 전 기능 무료

## 결론

- **QR 입장을 유료 게이트로 삼는다.** 이 제품에서 가장 완성도가 높고 검증된 기능이며,
  "10명은 이름 부르면 끝, 30명 넘으면 QR이 필요"라는 자연 규모 게이트다.
- **인원 종량 과금을 하지 않는다.** 스테이지 1회권 또는 월 구독, **둘 다 선불**.
  인원을 세지 않으므로 정산 배치·미수금·빌링키 실패 재시도가 전부 필요 없다.
- **결제 대금을 우리가 받지 않는다.** 무통장입금(참석자 → 주최자 계좌 직접)을 유지한다.
  타인의 자금을 매개하지 않으므로 전자금융업 규제 밖에 머문다 — 이것이 어스테이지의
  차별점(주최자 PG 수수료 0 · 정산 대기 0일 · 사업자등록 불필요)의 원천이다.
- **손익분기는 월 구독 8~10명이다.** 월 고정비가 66,150원(SES 이관 후)뿐이므로
  매출 극대화가 아니라 "손해 보지 않기"가 목적함수라면 이 이상 복잡할 필요가 없다.

## 기능 범위

### 무료 (영구·무제한)

스테이지 무제한 · 인원 무제한 · 예매 폼 · 명단 열람/검색/필터 · **수동 입금 확인(단건·일괄)**
· **명단 기반 수동 체크인** · 확정/취소 메일(입장번호만) · CSV 내보내기 · 현장 예매
· 현장 추첨 · 포스터 · 리치텍스트 · 비회원 조회 · 추가 구매 · 셀프 취소 · 커스텀 필드 3개

**+ 계정당 최초 1회 스테이지는 QR 포함 무료 체험** (`qr_trial_used_at` 컬럼 하나).
QR을 한 번 경험하지 않으면 살 이유를 모른다.

수동 체크인은 새로 만들 것이 없다 — 명단 상세 패널의 티켓별 입장 처리와 `forceCheckIn`이
그대로 동작한다. 30명까지는 이것으로 충분히 굴러간다.

### 의도적으로 무료에 남긴 것

- **CSV 내보내기** — 명단 열람과 기술적으로 분리되지 않는다(스태프 권한에서 이미 같은 결론).
  막아도 복붙으로 우회되고, "정산에 필요한 걸 막는다"는 인상이 나쁘다. 대신 가공 산출물인
  *정산 리포트*를 유료로.
- **현장 추첨** — 오히려 소규모 모임이 더 쓴다(북토크 경품). 바이럴 요소라 무료가 이득.
- **수동 입금 확인** — 막으면 유료 스테이지 운영 자체가 불가능하다. 무료 플랜의 뼈대.
- **현장 예매** — 규모와 무관하다.

## 폐기한 대안 (재논의 대상 아님)

아래는 **검토를 마치고 의도적으로 버렸다.** 다시 꺼내려면 이 문서의 근거부터 반박할 것.

### 1. PG 선지급 정산 (티켓 대금을 우리가 받고 수수료 떼고 정산)

가장 "이상적"으로 보이지만 **이상적인 형태가 아니라 다른 제품이다.**

- 타인의 자금을 수령·보관·정산하는 순간 **전자지급결제대행업(PG) 등록** 또는 PG사의
  플랫폼 상품(하위가맹점 구조)이 필요하다. → **주최자 한 명 한 명이 하위가맹점 심사 대상**이
  되어 신분증·계좌·경우에 따라 사업자등록을 요구하게 된다. 취미 모임 주최자에게 이건
  제품을 죽이는 마찰이다.
- 결제대금예치(에스크로) 또는 소비자피해보상보험 의무 발생 소지, 정산 자금 보유에 따른
  회계·세무·미정산 리스크.
- PG 수수료 2.8~3.4%를 주최자에게 물리면 "계좌이체는 공짜인데?", 참석자에게 물리면
  1만원 티켓에 예매수수료가 붙는다.
- **어스테이지의 유일한 차별점(수수료 0·즉시 입금·가입 마찰 0)을 스스로 버리게 된다.**
  하는 순간 이벤터스·페스타와 같은 링에서 열등한 복제품으로 싸운다.

> ⚠️ 자본금 요건·등록 면제 기준·에스크로 적용 범위는 2024년 전자금융거래법 개정으로 바뀐
> 부분이 있다. **실제 검토 시 전문가 확인 필수.** 다만 규제 무게가 이 사업 규모(월 원가
> 66,150원)와 자릿수가 맞지 않는다는 결론은 흔들리지 않는다.

### 2. 인원 종량 후불 과금 (인당 220원 누진 등)

정산 파이프라인 전체를 요구한다 — 인원 확정 시점 판정, 월 합산 청구, 빌링키 실패 재시도,
미수금 추심. **회수액이 월 9만원인 사업에 붙일 인프라가 아니다.** 인원 확정 시점 분쟁
(정원 기준이냐 실제 티켓 기준이냐)도 따라온다.

### 3. 크레딧 충전 방식 선불

미사용 잔액을 쌓아두면 **선불전자지급수단 발행업**으로 해석될 여지가 있다(2024 개정으로
규제 강화 영역). 회피법은 단순하다 — **충전 잔액 개념을 만들지 않고** 스테이지 1회권 또는
월 구독으로만 판다. 우리 서비스를 우리가 파는 것은 일반 재화 판매다.

### 4. 무통장입금 시스템 폐기

"우리가 돈 흐름 밖에 있다"는 **한계가 아니라 자산이다.** 폐기 대상이 아니고, 진짜 한계
(입금 대조 수동 노동)는 자동 대조 기능으로 푼다.

### 5. 참석자에게 예매 수수료 부과

우리가 대금을 받지 않으므로 참석자에게 직접 청구할 수단이 없다. 주최자가 티켓값에 얹어
받아 우리에게 넘기는 변형은 결국 주최자 부담과 동일하고 회수 문제도 같다.

## QR 게이트 설계 — `qr_enabled` 스냅샷

**지켜야 할 불변식:**

> **이미 티켓이 발급된 스테이지는 무슨 일이 있어도 잠기지 않는다.**

행사 당일 주최자 카드가 막혀 QR 스캔이 안 되는 것은 제품이 죽는 수준의 사고다. 이는
유료화를 포기할 이유가 아니라 **게이트 위치의 문제**다.

```
draft → open 전환 시 (updateEventStatus, src/app/actions/event.ts:286)
  플랜 검사 → events.qr_enabled = true 스냅샷
  이후 구독 만료·결제 실패에도 이 값은 절대 바뀌지 않는다
```

`bookings.unit_price`를 예매 시점에 못 박은 것과 **같은 패턴**이다. 스테이지 가격이 바뀌어도
기존 예매 금액이 흔들리지 않듯, 구독 상태가 바뀌어도 열린 스테이지의 QR은 흔들리지 않는다.
스태프에 대해서도 같은 규칙을 적용한다(진행 중 스테이지의 스태프는 만료 후에도 유지, 신규
초대만 차단).

**`booking_tickets.qr_token`은 무료 플랜에서도 항상 생성한다. 노출만 게이트한다.**
그래야 오픈 후 결제 시 그 자리에서 QR이 켜지고 기존 예매자에게 확정 메일을 재발송할 수 있다
— 업그레이드 경로가 살아 있어야 팔린다.

### 만료·결제 실패 시 동작

**데이터는 지우지 않고 "새로 만드는 것"만 막는다.** 이 규칙 하나로 전체가 설명된다.

| | 동작 |
| --- | --- |
| 참석자 측 전부 (예매·QR·입장·메일) | **영향 없음** |
| 진행 중 스테이지의 스태프 | **유지** — 신규 초대만 차단 |
| 커스텀 필드 5개짜리 기존 스테이지 | **그대로 동작** — 3개 초과 추가만 차단 |
| 입금 자동 대조 | 신규 수신 중단, 기존 알림 열람 가능 |
| 정산 리포트·일괄 메일·복제 | 잠금 |

### 구현 지점

| 지점 | 변경 |
| --- | --- |
| 마이그레이션 | `events.qr_enabled boolean not null default true` — **기존 스테이지는 전부 true** |
| | `subscriptions(user_id pk, plan, status, current_period_end)` — RLS SELECT 본인만, 쓰기는 service_role만 |
| `lib/plan.ts` (신규) | `canUse(plan, feature)` · `customFieldLimit(plan)` · `effectivePlan(sub, now)` — 순수 함수, vitest. `staff-permissions.ts`와 같은 패턴 |
| `actions/event.ts:286` `updateEventStatus` | draft→open 시 `assertPlan` + `qr_enabled` 스냅샷 |
| `lib/email.ts` `sendBookingConfirmation`·`sendBookingConfirmed` | `qr_enabled` 분기 — false면 QR 첨부 없이 입장번호만(40px 블록은 이미 있음) |
| `dashboard/events/[id]/scan/page.tsx` | `qr_enabled=false`면 진입 차단 + 업그레이드 안내 |

| `api/bookings/lookup`·`bookings/[id]`·`QRTicket.tsx`·`BookingLookup.tsx` | `qr_token` 응답·표시 게이트 |

- **게이트 기준은 스테이지 소유자다.** 스태프는 소유자 플랜을 따른다.
- `qr_token`을 참조하는 파일은 현재 8곳이다(`types/database.ts` 제외).

## 입금 자동 대조 설계

무통장입금의 최대 페인(100명이면 은행 앱 보며 100번 대조, 입금자명 불일치 빈발)을 없앤다.
**우리가 계좌에 접근하지 않고** 제공 가능하므로 규제 경계를 유지한다.

### 핵심 원칙

1. **자동 대조는 "제안"까지만. 확정 버튼은 사람이 누른다.** 오탐 비용이 크고 확정 즉시
   QR 확정 메일이 나가 되돌리기가 지저분하다. 이 기능의 출력은
   **`updateBookingStatusBulk`에 넘길 `bookingIds` 배열**이다 — 기존 액션(조건부 갱신 +
   메일 발송 + `updated`/`mailed` 카운트)을 한 줄도 고치지 않고 재사용한다.
2. **오픈뱅킹·스크래핑을 쓰지 않는다.** 주최자가 이미 받고 있는 알림을 전달받을 뿐이다.
3. **파싱·매칭은 순수 함수로 분리하고 vitest로 못 박는다.** (`lottery.ts`·`seats.ts` 패턴)

### 입력 경로 3개 — 하나로 정해지지 않는다

| 순위 | 경로 | 주최자 노동 | 커버리지 |
| --- | --- | --- | --- |
| **A** | 은행 **입금 알림 메일**을 전용 주소로 자동 전달 | 최초 1회 설정, 이후 0 | 은행별 상이 |
| **B** | 거래내역 **파일 업로드** (엑셀/CSV) | 행사마다 1회 | 사실상 전 은행 |
| C | 텍스트 붙여넣기 | 행사마다 1회 | PC 웹뱅킹만 |

- **모바일 뱅킹 앱은 거래내역 텍스트 선택이 안 된다.** C를 주 경로로 잡으면 안 된다.
- **A가 최선이지만 전제가 미확인이다** — 아래 "착수 전 확인할 것" 참조.
  특히 카카오뱅크·토스뱅크(소규모 모임이 가장 많이 쓴다)는 이메일 알림이 없을 가능성이 높다.
- **B가 실제 주 경로가 될 가능성이 높다.** `xlsx`는 SheetJS로 파싱하고, 은행별 컬럼은
  헤더 별칭 사전(`거래일시`/`거래일자`, `입금`/`입금액`/`받으신금액`, `내용`/`적요`/`보내는분`)
  으로 자동 감지하되 실패 시 컬럼 선택 UI로 떨어뜨린다. 한 번 매핑하면 저장해 재사용.
- **SMS 전달은 권하지 않는다** — Android는 서드파티 앱 설치, iOS는 사실상 불가.
- **셋 다 같은 파서·매처를 탄다.** 입력 어댑터만 3개.
- **채택률은 기능이 아니라 온보딩이 가른다.** 은행을 고르면 그 은행의 정확한 설정 경로를
  메뉴 이름·스크린샷과 함께 안내해야 한다. 은행 3~4곳만 먼저 지원하고 늘린다.

### 파싱 — `lib/deposit-parse.ts` (신규)

```ts
export type DepositNotice = {
  amount: number;
  depositorName: string | null;
  occurredAt: Date | null;
  bank: string | null;
};
export function parseDepositNotice(subject: string, body: string): DepositNotice | null;
```

은행별 정규식 어댑터. 실제 알림 문구를 픽스처로 넣고 테스트한다.

- **출금 알림을 입금으로 오인하지 말 것** — "입금"/"받으신금액" 키워드가 있는 건만 채택.
- **잔액 숫자를 금액으로 잡지 말 것** — 알림에 금액과 잔액이 나란히 나온다.
- **파싱 실패를 조용히 버리지 말 것** — `status='unparsed'`로 원문을 남기고 UI에 "직접 입력"
  으로 노출한다. 새 은행 포맷을 발견하는 유일한 경로다.

### 매칭 — `lib/deposit-match.ts` (신규)

```ts
export type MatchVerdict = "auto" | "review" | "unmatched";
export function matchDeposit(
  notice: DepositNotice,
  candidates: readonly MatchCandidate[]
): { bookingId: string; verdict: MatchVerdict; score: number; reasons: string[] }[];
```

후보군은 그 주최자의 진행 중 스테이지 `pending` 예매(취소 제외).

| 축 | 방법 | 비중 |
| --- | --- | --- |
| **금액** | `bookingAmount(b, event.price, effectiveQuantity(b))`와 정확 일치 | 필수 — 불일치면 후보 제외 |
| **입금자명** | `depositor_name ?? name` 정규화(공백·조사 제거) 후 정확일치 → 포함관계 → 초성 | 결정적 |
| **시각** | 알림 시각 − 예매 `created_at` 거리 | 동점 해소용 |

- 금액 일치 + 이름 일치 + **후보 유일** → `auto` (초록, 기본 체크)
- 금액 일치인데 이름 불일치 또는 **후보 여럿** → `review` (노랑, 체크 해제, 주최자 선택)
- 금액 불일치 → `unmatched` (회색, 수동 연결)

**최대 함정: 동일 금액 다건.** 1만원 티켓 스테이지에 1만원 입금 10건이 오면 금액만으로는
절대 못 가른다. 이름이 2축으로 필수고, 그래도 안 갈리면 `review`로 던진다 — 억지로 자동
확정하면 엉뚱한 사람에게 QR이 나간다.

- **부분 취소를 반드시 반영할 것** — `effectiveQuantity`를 써야 3매 중 1매 취소된 예매의
  기대 입금액이 맞는다. `quantity`를 쓰면 전부 틀린다.
- **추가 구매 고려** — 같은 이메일이 여러 예매를 가질 수 있으므로 후보는 이메일이 아니라
  예매 단위다.
- 금액 단가는 **반드시 `lib/booking-price.ts`** 를 통과한다(현장 예매가 다른 단가를 쓴다).

### 스키마 — `20260901100000_deposit_reconcile.sql`

```sql
create table deposit_inboxes (
  id uuid primary key default gen_random_uuid(),
  user_id uuid not null unique references auth.users on delete cascade,
  token uuid not null unique default gen_random_uuid(),  -- 주소의 +태그
  allowed_senders text[] not null default '{}',
  auto_confirm boolean not null default false,
  created_at timestamptz not null default now()
);

create table deposit_notices (
  id uuid primary key default gen_random_uuid(),
  inbox_id uuid not null references deposit_inboxes on delete cascade,
  dedup_key text not null,               -- hash(금액, 이름, 시각)
  raw_subject text, raw_body text,       -- 계좌번호 마스킹 후 저장
  from_address text, auth_pass boolean,  -- SPF/DKIM 검증 결과
  amount integer, depositor_name text, occurred_at timestamptz, bank text,
  status text not null default 'new',    -- new|matched|ignored|unparsed|quarantined
  matched_booking_id uuid references bookings on delete set null,
  matched_at timestamptz, matched_by uuid,
  received_at timestamptz not null default now(),
  unique (inbox_id, dedup_key)
);
```

- **dedup 필수** — 자동 전달 규칙과 수동 전달이 겹쳐 같은 알림이 두 번 온다.
- **RLS: 본인만 SELECT, 쓰기는 service_role만.** 입금 알림은 주최자 **개인 계좌 정보**이므로
  **스태프에게 노출하지 않는다.** 매트릭스에 `view_deposit_notices`를 owner 전용으로 추가.
  스태프는 기존 수동 입금 확인(`confirm_payment`)만 유지.
- **원문에 계좌번호가 들어간다.** 저장 전 계좌번호 패턴 마스킹 + 90일 자동 삭제.
  `select("*")` 금지 규칙이 여기도 그대로 적용된다.

## 함정

1. **`qr_token` 게이트는 UI가 아니라 API에서 한다.** UI에서만 감추면 RSC 페이로드에 그대로
   실려 간다 — 명단 `select("*")`에서 `password_hash`가 새던 것과 같은 함정.
2. **`api/check-in`에 `event_date` 비교를 넣지 말 것** — 사전 입장·리허설을 막는다.
   게이트는 권한·예매 상태·`qr_enabled` 셋뿐이다(CLAUDE.md 명시).
3. **`events.qr_enabled` 기본값은 `true`** — 기존 스테이지를 잠그면 배신이다.
4. **출시 시점 기존 사용자는 영구 Pro(Founding)로 둔다.** 원가가 사실상 0이고 홍보 자산이 된다.
5. **1회권 없이 구독만 팔지 말 것** — 비정기 주최자가 전량 이탈한다.
6. **자동 확정 기본값은 off.** 켜더라도 조건 4개(금액 정확일치 + 이름 정확일치 + 후보 유일 +
   발신자 화이트리스트·SPF/DKIM pass)를 모두 요구한다.
7. **참석자는 그 스테이지가 무료 플랜인지 유료인지 알 수 없어야 한다.**
8. **`usage_records` 원장은 어느 모델을 택하든 심어두면 이득이다** — 과금용이 아니라
   "무료 티어가 어디서 깨지는지" 감시용.
